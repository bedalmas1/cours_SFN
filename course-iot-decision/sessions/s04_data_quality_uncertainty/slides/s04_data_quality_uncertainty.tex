\begin{frame}{Bienvenue dans la séquence 4}
  \begin{block}{Ce que nous ajoutons aujourd'hui}
    Jusqu'ici, nous avons supposé que les valeurs numériques présentes dans un message étaient au moins plausibles. Aujourd'hui, nous arrêtons de le supposer.
  \end{block}
  \begin{itemize}
    \item Une valeur peut être présente sans être valide : un champ manquant ailleurs dans le même message, une unité incohérente, ou une valeur physiquement impossible peuvent toutes se cacher derrière un nombre d'apparence normale.
    \item Un silence dans une chronologie de mesures peut être un vrai manque de message, ou seulement la conséquence du rejet d'une ligne invalide : ces deux silences se ressemblent, mais n'appellent pas la même vérification.
    \item Nous allons construire, sur nos propres données, la différence entre ces deux formes de silence -- et voir pourquoi la confondre peut fausser une décision.
  \end{itemize}
\end{frame}

\begin{frame}{Ce que vous saurez faire à la fin de cette séquence}
  \begin{enumerate}
    \item nommer et détecter quatre types d'erreurs de contenu : champ manquant, unité incohérente, valeur hors plage physique, incohérence temporelle ;
    \item séparer les messages propres des messages rejetés sans jamais corriger silencieusement une valeur ;
    \item distinguer un silence réel dans une chronologie d'un silence simplement expliqué par une ligne rejetée ;
    \item relier un silence non expliqué à la confiance que l'on peut accorder à une valeur qui le suit ;
    \item recommander une action avec confiance, preuves, incertitudes et vérification terrain.
  \end{enumerate}
\end{frame}

\begin{frame}{La question qui guidera la séance}
  \decisionquestion{À partir de quel niveau d'erreur et de silence une alerte température devient-elle insuffisante pour agir seule ?}
  \begin{itemize}
    \item Nous ne cherchons pas un seuil universel d'erreur acceptable, mais une méthode pour qualifier, cas par cas, ce qu'un lot de données permet réellement d'affirmer.
    \item Une même valeur d'alerte peut être défendable ou fragile selon ce qui l'entoure : son contexte, ses voisines, et surtout les silences qui la précèdent.
    \item Le raisonnement compte autant que la conclusion : deux décisions différentes peuvent être également recevables si les preuves et les limites sont explicites.
  \end{itemize}
\end{frame}

\begin{frame}{Le scénario : une alerte apparaît}
  \begin{columns}[T]
    \column{.55\textwidth}
    Une supervision transmet un message unique : « \texttt{battery-shelter-01} a atteint 36,2\,°C, au-dessus du seuil habituel. » Aucune autre information n'accompagne cette phrase.
    \column{.4\textwidth}
    \begin{block}{Contrainte de décision}
      Vous ne savez ni si cette valeur est isolée, ni si elle a été précédée d'un silence, ni si le message qui la porte respecte les règles de qualité que nous allons définir.
    \end{block}
  \end{columns}
  \vfill
  \alert{La première question n'est donc pas « la valeur est-elle haute ? », mais « cette valeur est-elle même une donnée sur laquelle on peut raisonner ? »}
\end{frame}

\begin{frame}{Avant de regarder les données : votre décision}
  \begin{columns}[T]
    \column{.5\textwidth}
    Choisissez une réponse :
    \begin{enumerate}
      \item[A.] l'alerte est exploitable telle quelle ;
      \item[B.] il faut d'abord contrôler la qualité des données ;
      \item[C.] maintenir l'activité par prudence en attendant ;
      \item[D.] suspendre l'activité par prudence en attendant.
    \end{enumerate}
    \column{.42\textwidth}
    Notez également :
    \begin{itemize}
      \item votre confiance de 0 à 100 \% ;
      \item votre raison principale ;
      \item l'information qui vous manque le plus.
    \end{itemize}
  \end{columns}
  \vfill
  \alert{Ce vote initial sera comparé au vote final, une fois le contrôle qualité effectué sur les données réelles.}
\end{frame}

\begin{frame}{Une valeur n'est pas encore une donnée validée}
  \begin{description}
    \item[Valeur] un nombre, isolé de tout contrôle : « 36,2 ».
    \item[Message] cette valeur replacée dans un message complet, avec un champ censé porter son unité, son horodatage et sa zone.
    \item[Donnée validée] un message dont chaque champ obligatoire est présent, dont l'unité est reconnue, et dont la valeur reste physiquement plausible.
    \item[Décision] une action choisie en tenant compte de ce que la donnée validée permet, ou non, d'affirmer.
  \end{description}
  \begin{block}{Le piège de cette séquence}
    Un message peut franchir les trois premières étapes en apparence -- il ressemble à un message normal -- tout en échouant silencieusement à l'une d'elles. Nous allons apprendre à le détecter avant qu'il n'atteigne une décision.
  \end{block}
\end{frame}

\begin{frame}{Auto-vérification avant de continuer}
  \small
  \begin{block}{Une alerte réduite à une seule phrase prouve-t-elle quoi que ce soit sur la qualité de la donnée qui la porte ?}
    Non : elle ne dit rien sur la présence de tous les champs attendus, sur la cohérence de l'unité, ni sur la plausibilité physique de la valeur. Ces propriétés ne se voient qu'en examinant le message complet.
  \end{block}
  \begin{block}{Pourquoi distinguer « valeur », « message » et « donnée validée » ?}
    Parce qu'une même valeur numérique peut appartenir à un message par ailleurs invalide : la valeur seule ne suffit jamais à juger de la qualité de l'ensemble.
  \end{block}
\end{frame}

\begin{frame}[plain]
  \centering
  \Huge Section 2\\[3mm]
  \Large Quatre qualités d'une donnée
  \vfill
  \normalsize Avant de coder le moindre contrôle, nous devons savoir précisément ce que chaque contrôle est censé vérifier.
\end{frame}

\begin{frame}{Validité}
  \begin{block}{Définition}
    La ligne respecte les règles déclarées : chaque champ obligatoire est présent, l'unité appartient au vocabulaire attendu, et la valeur reste dans une plage physiquement plausible.
  \end{block}
  \begin{itemize}
    \item \textbf{Piège fréquent :} confondre « le champ existe dans le JSON » avec « le champ contient une valeur correcte ».
    \item \textbf{Effet sur la décision :} une ligne invalide ne doit jamais entrer dans un calcul d'indicateur sans avoir été signalée au préalable.
  \end{itemize}
  \decisionquestion{Un message peut-il être syntaxiquement correct -- un JSON qui se parse sans erreur -- tout en étant invalide au sens de cette séquence ?}
\end{frame}

\begin{frame}{Complétude}
  \begin{block}{Définition}
    Tout ce qui était attendu sur une période donnée est effectivement arrivé : aucune zone, aucun instant de mesure attendu ne manque silencieusement.
  \end{block}
  \begin{itemize}
    \item \textbf{Piège fréquent :} confondre un message reçu puis rejeté avec un message qui n'a jamais été reçu du tout.
    \item \textbf{Effet sur la décision :} un vrai manque de transmission et un rejet de qualité n'appellent pas la même vérification terrain.
  \end{itemize}
  \alert{Nous reviendrons sur ce piège précis dans l'incident de fin de séance : c'est le cœur de la séquence.}
\end{frame}

\begin{frame}{Cohérence}
  \begin{block}{Définition}
    Les champs d'une même ligne, ou de lignes voisines dans le temps, ne se contredisent pas entre eux.
  \end{block}
  \begin{exampleblock}{Exemple réel du lot}
    Un message de \texttt{it-room-01} déclare \texttt{measured\_at = 2026-10-19T10:15:00Z} alors qu'il a été \texttt{received\_at = 2026-10-19T09:55:00Z}, soit vingt minutes \emph{avant} l'instant où il prétend avoir été mesuré. Une mesure ne peut pas être reçue avant d'avoir eu lieu.
  \end{exampleblock}
  \textbf{Effet sur la décision :} une incohérence temporelle invalide la ligne entière ; elle ne se corrige pas en gardant une seule des deux horloges.
\end{frame}

\begin{frame}{Précision}
  \begin{block}{Définition}
    La mesure reflète un ordre de grandeur physiquement crédible pour le contexte décrit -- ici, la température ambiante d'un abri sur une base aérienne.
  \end{block}
  \begin{itemize}
    \item \textbf{Piège fréquent :} croire qu'une valeur numérique plausible en apparence est forcément exacte physiquement.
    \item \textbf{Effet sur la décision :} aucun contrôle automatique de cette séquence ne peut démontrer l'exactitude d'une mesure ; il peut seulement écarter ce qui est physiquement impossible.
  \end{itemize}
  \alert{Rejeter une valeur hors plage n'est pas la même chose que valider les valeurs restantes : cela ne fait qu'écarter le pire des cas.}
\end{frame}

\begin{frame}[fragile]{Un exemple filé : le message incomplet d'it-room-01}

{"topic":"airbase/batch002/it-room-01/temperature/0002",
 "received_at":"2026-10-19T09:51:00Z","retained":true,
 "payload":{"batch_id":"alert-window-002","message_id":"it-room-01-0002",
  "site_id":"base-projetee-alpha","zone":"it-room-01","asset_type":"tactical_it",
  "sensor":"temperature","measured_at":"2026-10-19T09:50:00Z",

\begin{frame}{Auto-vérification avant de continuer}
  \small
  \begin{block}{Validité et précision sont-elles la même qualité ?}
    Non : la validité contrôle la forme et la plausibilité déclarative (champs, unité, plage) ; la précision porterait sur l'exactitude physique réelle, que nos contrôles ne peuvent pas démontrer.
  \end{block}
  \begin{block}{Pourquoi un message avec un JSON parfaitement valide peut-il être invalide au sens de cette séquence ?}
    Parce que la validité JSON ne garantit ni la présence de chaque champ métier obligatoire, ni la cohérence entre ses champs, ni la plausibilité physique de sa valeur.
  \end{block}
  \begin{block}{Que retenir du message d'\texttt{it-room-01} ci-dessus ?}
    Qu'une valeur présente et plausible ne suffit pas : l'absence du seul champ \texttt{unit} rend toute la ligne invalide, malgré une valeur en apparence normale.
  \end{block}
\end{frame}

\begin{frame}{Zoom : l'unité incohérente}
  Le message \texttt{maintenance-zone-01-0002} déclare \texttt{value = 86.9} avec \texttt{unit = "fahrenheit"}, au milieu de quatre autres messages de la même zone tous exprimés en Celsius.
  \begin{block}{Le calcul qui aurait été silencieusement faux}
    86,9\,°F correspond à environ 30,5\,°C -- une valeur en fait cohérente avec ses voisines. Sans le contrôle d'unité, ce message aurait été traité comme 86,9\,°C : une aberration invisible dans un tableau, mais catastrophique dans un calcul de maximum.
  \end{block}
  \alert{Nous ne convertissons jamais silencieusement l'unité : nous rejetons et documentons, pour que l'erreur de configuration reste visible.}
\end{frame}

\begin{frame}{Zoom : la valeur hors plage physique}
  Le message \texttt{optronics-shelter-01-0002} déclare \texttt{value = 214.7} en \texttt{celsius}, entouré de quatre valeurs voisines entre 27,9 et 28,3\,°C.
  \begin{block}{Bornes retenues pour cette séquence}
    -10\,°C à 60\,°C. Ce ne sont pas des bornes officielles ni une spécification du fabricant : ce sont des bornes pédagogiques, à faire valider par le responsable du matériel avant tout usage réel.
  \end{block}
  \decisionquestion{Si cette valeur n'avait pas été écartée, quel effet aurait-elle eu sur le maximum calculé pour cette zone ?}
\end{frame}

\begin{frame}{Le doublon exact : une retransmission, pas un candidat}
  \small
  Le message \texttt{comms-shelter-01-0001} apparaît deux fois dans le brut : même topic, même \texttt{message\_id}, même mesure, même horodatage de mesure -- seul l'instant de réception diffère de quatre secondes.
  \begin{alertblock}{Deux sortes de ressemblance, à ne jamais confondre}
    Un \emph{candidat} doublon partage des valeurs semblables mais porte des identifiants différents : on ne le supprime jamais sans règle explicite, car deux capteurs distincts peuvent légitimement mesurer la même valeur au même instant. Ici, c'est l'inverse : l'identifiant, le topic et la mesure sont rigoureusement identiques -- une retransmission du même événement, probablement liée au mécanisme de re-livraison de MQTT.
  \end{alertblock}
  \normalsize Ce cas précis est le seul de cette séquence où retirer une ligne ne perd aucune information : les deux occurrences décrivent le même événement, pas deux événements distincts.
\end{frame}

\begin{frame}{Auto-vérification avant de continuer}
  \small
  \begin{block}{Pourquoi ne pas convertir silencieusement 86,9\,°F en Celsius plutôt que rejeter le message ?}
    Parce que corriger silencieusement masquerait l'erreur de configuration qui a produit cette unité incorrecte, et empêcherait de la détecter ailleurs dans le système.
  \end{block}
  \begin{block}{En quoi le doublon exact de \texttt{comms-shelter-01} diffère-t-il d'un simple candidat doublon ?}
    Un candidat doublon partage des valeurs semblables avec des identifiants différents et reste ambigu ; le doublon exact ici partage un identifiant, un topic et une mesure rigoureusement identiques : c'est la même publication reçue deux fois.
  \end{block}
\end{frame}

\begin{frame}[plain]
  \centering
  \Huge Section 4\\[3mm]
  \Large Rejet, correction, quarantaine
  \vfill
  \normalsize Détecter une erreur ne dit pas encore quoi en faire : trois réponses sont possibles, une seule est appliquée ici.
\end{frame}

\begin{frame}{Rejet, correction, quarantaine}
  \begin{description}
    \item[Rejet] écarter la ligne du calcul, en conservant sa trace complète et sa raison exacte dans un fichier séparé.
    \item[Correction] remplacer une valeur jugée fautive par une valeur jugée plus probable, silencieusement ou explicitement.
    \item[Quarantaine] isoler une ligne ambiguë sans la valider ni la rejeter définitivement, en attendant un avis humain ou une vérification externe.
  \end{description}
  \begin{alertblock}{Choix retenu dans cette séquence}
    Le rejet, systématiquement documenté. Aucune correction automatique n'est appliquée : convertir une unité ou ajuster une valeur resterait une hypothèse, jamais une observation.
  \end{alertblock}
\end{frame}

\begin{frame}{Pourquoi ce cours ne corrige jamais silencieusement}
  \begin{itemize}
    \item Une correction silencieuse remplace une observation par une hypothèse, sans que quiconque relisant le fichier plus tard ne puisse s'en rendre compte.
    \item Elle rend impossible la détection d'un problème récurrent : si l'unité Fahrenheit est corrigée automatiquement partout, personne ne remarquera qu'un capteur reste mal configuré.
    \item Elle transfère silencieusement la responsabilité du jugement de l'humain vers un script, sans trace du raisonnement suivi.
  \end{itemize}
  \decisionquestion{Existe-t-il un cas, dans ce lot, où une quarantaine aurait été plus appropriée qu'un rejet ferme ?}
\end{frame}

\begin{frame}{Auto-vérification avant de continuer}
  \small
  \begin{block}{Un silence expliqué par un rejet est-il sans importance pour la décision ?}
    Non : il reste un signal sur la qualité de la source à surveiller ; il n'est simplement pas un signal d'absence de transmission comme celui de \texttt{battery-shelter-01}.
  \end{block}
  \begin{block}{Peut-on affirmer que \texttt{battery-shelter-01} est en panne à partir de ce seul silence ?}
    Non : le silence a plusieurs causes possibles -- panne, coupure de transmission, filtre d'extraction incorrect, ou hausse réelle simplement non enregistrée -- que seule une vérification terrain ou technique peut départager.
  \end{block}
